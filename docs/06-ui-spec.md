# 06 前端 UI 规范

设计原则:**克制**。一个页面一个主要动作。屏幕上同时可见的可操作元素尽量不超过 7 个。
参考感觉:苹果式的留白、清晰层级、少即是多。不要模仿具体产品,不要装饰性元素。

## 1. 页面状态机(单页应用,没有路由跳转)

```
Empty → Uploading → Analyzing → Ready(选目标 + 试听) → Exporting → Done
   ↑         └──────────── Error ────────────┘             │
   └──────────────────── "处理另一首" ──────────────────────┘
```

| 状态 | 屏幕上有什么 | 主要动作 |
|---|---|---|
| Empty | 标题、一句话说明、拖放区 | 选择/拖入文件 |
| Uploading | 文件名、进度条 | 取消 |
| Analyzing | 简短提示"正在听这首歌…"、进度 | (无) |
| Ready | 播放器、A/B 切换、4 个目标、强度滑块、"导出"、"处理详情"入口 | 选目标、听、导出 |
| Exporting | 格式选择已确认后的进度 | (无) |
| Done | 下载按钮、结果摘要、"处理另一首" | 下载 |
| Error | 中文错误信息、"重试"/"换一首" | 重试 |

## 2. Ready 界面布局(示意)

```
Audio Lab

  ┌──────────────────────────────────────────────┐
  │  song-name.mp3                      3:07     │
  │  ▶   ━━━━━━━●━━━━━━━━━━━━━━━━━━━━━━━         │
  │                                              │
  │           [ 原曲 ]   [ 处理后 ]              │   ← A/B 分段控件
  └──────────────────────────────────────────────┘

  想要什么样的声音?
  ( 均衡清晰 )  ( 温暖醇厚 )  ( 明亮通透 )  ( 紧实有力 )

  强度        ○━━━━━━━●━━━━━━  70%

  ✓ 已减轻低中频浑浊                    处理详情 ›

                                          [ 导出 ]
```

规则:
- 目标是单选卡片/胶囊,选中状态用强调色
- 强度滑块变化后 400 ms 防抖,再请求 resolve + preview;请求期间 B 保持上一个可播放版本,并显示细小的"更新中"状态,**不阻塞播放**
- 提示文案(notes/warnings)最多显示 2 条,多的收进"处理详情"
- "处理详情"在右侧抽屉或下方折叠面板展开,不跳页,不弹模态框叠模态框

### 导出面板(M5)

点"导出"后在原位展开一个简洁面板(不用模态框):
- 格式三选一:WAV(无损)/ FLAC(无损,更小)/ MP3(通用),默认 WAV
- 音量三选一:"适合流媒体(-14)"(默认)/"稍轻(-16)"/"保持原曲音量";括号里的数字不显示,界面上只写中文
- 一个确认按钮"开始导出"。导出中显示进度,完成进入 Done 状态

## 3. A/B 试听(Web Audio)

- 两个 `AudioBuffer`(原曲段、处理段)同时加载,各接一个 `GainNode`,增益来自 `gain_original_db` / `gain_processed_db`(转线性 `10^(dB/20)`)
- 切换 A/B 时:**播放位置不变**,只切换哪个 GainNode 为 1/0(用 10 ms 线性斜坡避免爆音)
- 空格:播放/暂停。`A` / `B` 键或左右方向键:切换。播放条可拖动,范围为这 30 秒
- 默认首次播放播的是"处理后",并有一行小字说明"已按相同音量对比"
- 页面切到后台/播放结束:不自动循环,除非用户开启"循环"(M3 不做)

## 4. 处理详情(M6 才实现编辑;M3–M5 只读列表)

展示 recipe 中每个节点:名称(中文)、是否启用、参数。
M6:参数可改,改后点"应用"重新预览。显示时用中文名 + 括号里英文术语,例如"均衡(EQ)"。这是前端唯一允许出现专业术语的地方。

## 5. 视觉规范(设计令牌,写在 `web/src/styles/tokens.css`)

只用这些变量,不在组件里写死颜色/尺寸:

```
--bg:            #FFFFFF  (深色模式 #000000)
--bg-elevated:   #F5F5F7  (深色 #1C1C1E)
--text:          #1D1D1F  (深色 #F5F5F7)
--text-secondary:#6E6E73  (深色 #98989D)
--accent:        #0A7AFF  (深色 #409CFF)
--danger:        #D70015
--radius:        12px
--space-1..6:    4 / 8 / 12 / 16 / 24 / 40 px
--font:          -apple-system, BlinkMacSystemFont, "PingFang SC", "Noto Sans SC", "Segoe UI", sans-serif
--shadow:        0 1px 2px rgba(0,0,0,.06)(只在浮层使用)
```

- 跟随系统浅色/深色(`prefers-color-scheme`)
- 正文 16px,说明 13–14px,标题 28–34px;字重只用 400/500/600
- 触控目标至少 44×44 px
- 动效:只有状态变化用 150–250 ms 的淡入/位移;尊重 `prefers-reduced-motion`
- 响应式:最小宽度 360 px;窄屏时目标卡片变 2×2 网格

## 6. 文案(`web/src/copy.zh.ts`)

所有用户可见文字集中管理。风格:简短、口语、不用术语。示例:

- 标题:"让声音,变得更好"
- 说明:"上传一首歌,选你想要的声音。"
- 拖放区:"把歌曲拖到这里,或点击选择" / "支持 WAV、MP3、FLAC、M4A,10 分钟内"
- 分析中:"正在听这首歌…"
- 错误:`FILE_TOO_LARGE` → "文件太大了(最大 80 MB)";`DURATION_TOO_LONG` → "歌曲太长了(最长 10 分钟)";`DECODE_FAILED` → "这个文件打不开,换一个试试";其他错误码也要各有一条文案,另有一个通用兜底
- 警告码 → 文案(例):`bandwidth_limited` → "这首歌的高频本来就不多,所以没有增加高频";`already_loud` → "这首歌本来就很响,提升空间有限";`has_clipping` → "原曲已有爆音,无法修复"

## 7. 无障碍

- 所有控件可键盘操作,有可见焦点
- A/B 分段控件用 `role="tablist"` 或等价语义;滑块用原生 `<input type="range">` 并有 `aria-label`
- 状态变化(分析完成、预览更新)通过 `aria-live="polite"` 区域播报
- 对比度 ≥ 4.5:1

## 8. 禁止清单

- 不出现 EQ、压缩、LUFS、dB 等术语(处理详情除外)
- 不出现超过一层的菜单,不出现模态框套模态框
- 不加广告位、推荐位、"升级"提示、社交分享
- 不加没有被 recipe 支撑的"效果"(例如假的"AI 魔法"按钮)
- 不在前端做任何音频处理(除 A/B 播放与增益)

## 9. 前端测试要求

- 状态机:每个状态转换一个单元测试(reducer 级别)
- A/B 增益换算:`dB → 线性` 的数值测试
- 错误码 → 文案映射:每个后端错误码都有文案(测试遍历 `openapi.json` 里的错误码枚举)
- 一个冒烟测试(vitest + Testing Library,mock `fetch`,不引入新依赖):上传 → 选目标 → 出现播放器 → 导出按钮可点
